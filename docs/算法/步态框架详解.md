# 步态框架详解

> 四层架构：轨迹层 → 步态层 → 腿控制层 → 舵机驱动层。每一层只做一件事。

---

## 一、整体架构

```
┌─────────────────────────────────────────────┐
│  gait.c         步态层                       │
│  决定四条腿"什么时候抬、抬多高、迈多远"        │
│  ↓ 调用 Leg_SetJoint(leg, joint, angle)     │
├─────────────────────────────────────────────┤
│  leg_control.c  腿控制层                     │
│  把"第几条腿的哪个关节多少度"翻译成舵机编号     │
│  ↓ 调用 NewServo_SetAngle(servo_n, angle)   │
├─────────────────────────────────────────────┤
│  new_servo.c    舵机驱动层                    │
│  把 0~270° 翻译成 500~2500μs 脉宽写 TIM CCR  │
│  ↓ __HAL_TIM_SET_COMPARE()                  │
├─────────────────────────────────────────────┤
│  硬件                                        │
│  TIM2/3/4/12 → 12路50Hz PWM → 12个270°舵机   │
└─────────────────────────────────────────────┘
```

**为什么分四层？**

每一层的职责互不重叠。比如你想换舵机型号（改成 180° 舵机），只需改 `new_servo.c` 的角度→脉宽映射公式，往上两层完全不动。反过来，你想改步态算法，只改 `gait.c`，往下两层也不用管。这就是分层的好处：**改一块不影响其他块**。

## 二、第一层：舵机驱动 (new_servo.c)

### 2.1 核心公式

```c
pulse = (angle × 2) / 27 + 5
```

| 角度 | 计算过程 | pulse(CCR) | 物理脉宽 |
|------|---------|-----------|---------|
| 0° | (0×2)/27+5 | 5 | 0.5ms |
| 135° | (135×2)/27+5 | 15 | 1.5ms |
| 270° | (270×2)/27+5 | 25 | 2.5ms |

**为什么 CCR 值 5~25 对应 0.5~2.5ms？**

这是 TIM 的 PSC 和 ARR 共同决定的。CubeMX 里配了 `PSC=23999, ARR=199`：

```
定时器时钟 = 240MHz / (PSC+1) = 240MHz / 24000 = 10kHz
每个 CCR 单位 = 1 / 10kHz = 0.1ms

CCR=5  → 5×0.1ms = 0.5ms  (舵机 0°)
CCR=15 → 15×0.1ms = 1.5ms  (舵机 135°)
CCR=25 → 25×0.1ms = 2.5ms  (舵机 270°)
```

**为什么公式写成 `(angle × 2) / 27` 而不是 `angle × 20 / 270`？**

```
角度范围 270°，CCR 范围 20（25-5=20）
每度 = 20/270 = 2/27 个 CCR 单位

CCR = angle × (2/27) + 5
    = (angle × 2) / 27 + 5      ← 整数运算，无浮点
```

整数运算避免浮点，STM32H7 上整数除法是硬件单周期指令，比软件浮点快几十倍。而且 nano.specs 下 `%f` 会崩，所以整个工程都刻意避免浮点运算。

### 2.2 `NewServo_SetAngle()` 的 switch-case

12 个 case，每个对应一个 `__HAL_TIM_SET_COMPARE(tim, ch, pulse)`。

**为什么不写成数组循环？**

因为 TIM 句柄和通道是编译期常量，`__HAL_TIM_SET_COMPARE` 是宏展开成直接寄存器写：

```c
// 展开后 ≈
htim2.Instance->CCR1 = pulse;   // 一条 STR 指令
```

如果写成数组索引，就要在运行时查表跳转，多好几条指令。对 12 路舵机每帧都调用（120 次/秒），这点开销累积起来就不可忽略了。switch-case 编译器会优化成跳转表，和直接写寄存器几乎一样快。

### 2.3 `NewServo_BatchControl()` — 批量写入

先预计算 12 个 CCR 值，再一口气写完。目前 gait.c 没用这个函数（用了逐腿调用），但后续如果加了逆运动学需要整帧原子更新，这个函数就可以直接用。

## 三、第二层：腿控制 (leg_control.c)

### 3.1 映射表

```c
static const uint8_t servo_map[4][3] = {
    {  1,  5,  9 },   // Leg 1: 外展=舵机1, 大腿=舵机5, 小腿=舵机9
    {  2,  6, 10 },   // Leg 2
    {  3,  7, 11 },   // Leg 3
    {  4,  8, 12 },   // Leg 4
};
```

**为什么 `servo_map[4][3]` 是 `uint8_t`？**

舵机编号 1~12，一个 byte 够用。`uint8_t` 省 RAM——虽然这个表只有 12 字节，但这是习惯问题：能用小的就不用大的。

**为什么是 `[leg][joint]` 这个顺序？**

因为调用方总是知道"第几条腿的哪个关节"——步态算法不关心舵机编号，它只关心腿和关节。映射表把"逻辑关节"翻译成"物理舵机"，调用方完全不需要知道舵机 1 在 PA0、舵机 5 在 PB0 这些细节。

### 3.2 `Leg_SetJoint(leg, joint, angle)` — 核心接口

```c
void Leg_SetJoint(uint8_t leg, uint8_t joint, uint16_t angle)
{
    if (leg > LEG_4 || joint > JOINT_CALF) return;  // 越界保护
    NewServo_SetAngle(servo_map[leg][joint], angle);  // 查表 + 转调
}
```

这是步态层唯一调用的接口。只做两件事：**校验 + 转发**。没有角度限幅——限幅在 gait.c 里用 CLAMP 宏做，因为只有 gait.c 知道当前运动状态下角度应该限制到什么范围。

### 3.3 `Leg_Init()` — 缓启动

```
放松姿态（90°）→ 15步渐进 → 站立姿态（1.5秒）
```

**为什么需要？** 上电瞬间 12 个舵机同时从随机位置猛拉到站立角，电流尖峰可达 12×2A=24A，足以让板子复位。渐进逼近把电流分散到 1.5 秒内。

`Leg_AllStand()` 直接跳到站立角，适合运行时复位姿态，前提是舵机已经在附近——不用缓启动。

## 四、第三层：步态引擎 (gait.c)

这是整个框架最核心的一层。

### 4.1 相位驱动模型

**核心概念：把步态抽象成一个转动的时钟。**

```
全局相位 g_phase: 0 → 1 → 2 → ... → 359 → 0 → ...

       0°(最前)
         ↑
   90° ← + → 270°
         ↓
       180°(最后)
```

每条腿有自己的 **相位偏移** `offset[leg]`，所以：

```
local_phase = (g_phase + offset[leg]) % 360
```

**为什么用相位而不是时间？**

因为时间会溢出（`uwTick` 每 49 天归零），而相位永远在 0~359 之间循环。更重要的是，相位让四条腿的关系一目了然：

- offset 差 180° → 两条腿完全反相（一条抬一条蹬）
- offset 差 90° → 错开 1/4 周期
- offset 相同 → 同步

**为什么范围是 0~359 而不是 0~2π 弧度？**

整数运算。`% 360` 是整数取模，单周期指令。如果用浮点弧度 `0~2π`，每一步都要浮点乘除和 `fmod()`——在无 FPU 硬件的场景下这很慢。

### 4.2 周期两分：摆动相 vs 支撑相

```
一个 360° 周期 = 摆动相(180°) + 支撑相(180°)

摆动相 (0~179°):  腿在空中
  - 大腿从最前摆到最后    → 向前迈
  - 小腿弯膝抬离地面      → 不拖地

支撑相 (180~359°): 腿在地上
  - 大腿从最后蹬到最前    → 推身体前进
  - 小腿伸直贴地          → 提供支撑力
```

**为什么两半各占 180° 而不是自定义比例？**

简化。50/50 占空比在大多数步态下都工作良好。后续如果要做"跑跳"步态（腾空时间长于着地时间），可以把分界点从 180 改成可配置参数。

### 4.3 轨迹函数

#### swing_traj — 摆动相轨迹

```c
static void swing_traj(uint16_t phase, int16_t *thigh_delta, int16_t *calf_delta)
{
    // thigh: phase=0→最前(+STEP_LENGTH), phase=90→正中(0), phase=179→最后(-STEP_LENGTH)
    *thigh_delta = (int16_t)(GAIT_STEP_LENGTH * (90 - (int32_t)phase)) / 90;

    // calf: 正弦波，phase=0/179→低(0), phase=90→最高(STEP_HEIGHT)
    if (phase <= 90)
        *calf_delta = (int16_t)(GAIT_STEP_HEIGHT * (int32_t)phase) / 90;
    else
        *calf_delta = (int16_t)(GAIT_STEP_HEIGHT * (180 - (int32_t)phase)) / 90;
    *calf_delta = -*calf_delta;  // 负值 = 膝盖弯曲
}
```

**大腿轨迹是线性下降：**

```
thigh_delta
  +40 ┤╲
      ┤ ╲
    0 ┤──┼──  phase 90°
      ┤   ╲
  -40 ┤    ╲
      ┤
      0°──────179°
```

**为什么是线性？** 最简单的能用的曲线。后续可以改成摆线（cycloid）或贝塞尔曲线让运动更平滑，但现在线性就够了——先跑起来再优化。

**小腿轨迹是三角波（近似正弦）：**

```
calf_delta
    0 ┤╲    ╱
      ┤ ╲  ╱
  -30 ┤──╲╱──
      ┤
      0°──90°──179°
```

**为什么用三角波而不是真正弦？** 整数运算。三角波用乘法和除法就够了，正弦需要查表或浮点。三角波和正弦在抬腿这个场景下差异很小——腿抬起来的高度差不多就行，不需要亚毫米精度。

**为什么 `*calf_delta = -*calf_delta` 取反？**

因为驼机角度语义：角度减小 = 膝盖弯曲（小腿往大腿收）。抬腿时小腿要弯曲，所以 calf_delta 必须是负值。

#### stance_traj — 支撑相轨迹

```c
static void stance_traj(uint16_t phase, int16_t *thigh_delta, int16_t *calf_delta)
{
    uint16_t p = phase - 180;   // 归一化到 0~179
    *thigh_delta = (int16_t)(GAIT_STEP_LENGTH * (90 - (int32_t)p)) / 90;
    *calf_delta = 0;             // 支撑相小腿贴地, 不屈膝
}
```

**为什么和 swing_traj 的大腿轨迹一模一样？**

对称设计。摆动相大腿从 `+STEP_LENGTH` 扫到 `-STEP_LENGTH`（向前迈），支撑相也从 `+STEP_LENGTH` 扫到 `-STEP_LENGTH`（向后蹬）。虽然轨迹公式一样，但语义不同——这保证了腿回到着地点时位置和上一周期衔接，不会越走越歪。

**为什么 `calf_delta = 0`？**

支撑相腿在地上，膝盖必须伸直才能把身体撑起来。如果支撑相也屈膝，机器人会蹲着走——又慢又费电。

### 4.4 四种步态的本质

```c
static const uint16_t gait_offsets[GAIT_NUM][4] = {
    /* STAND */ {   0,   0,   0,   0 },
    /* TROT  */ {   0, 180, 180,   0 },
    /* WALK  */ {   0,  90, 180, 270 },
    /* CRAWL */ {   0, 120, 240,  60 },
};
```

**所有步态的差异仅仅是一行数字。** 因为轨迹函数 `swing_traj`/`stance_traj` 只看 `local_phase`，而 `local_phase` 由 offset 决定。所以：

| 步态 | offset 规律 | 效果 |
|------|-----------|------|
| STAND | 全 0 | 四条腿同相 → 都站着不动 |
| TROT | `0,180,180,0` | 腿1+4 一组, 腿2+3 一组, 对角交替 |
| WALK | `0,90,180,270` | 依次错开 90°, 一次只抬一条腿 |
| CRAWL | `0,120,240,60` | 错开 120°/60°, 身体重心更低 |

**为什么 TROT 的配对是 (1,4) 和 (2,3) 而不是 (1,3) 和 (2,4)？**

因为腿的编号是：

```
      前
  腿1    腿2
  腿3    腿4
      后
```

(1,4) 是左前+右后，(2,3) 是右前+左后——正好两条对角线。对角线运动时重心始终在另外两条支撑腿的连线上，不会侧翻。

**为什么 WALK 偏移是 0/90/180/270 而不是 0/180/90/270？**

0/90/180/270 保证抬腿顺序是 1→2→3→4，绕身体一圈。如果换成 0/180/90/270，抬腿顺序变成 1→3→2→4——每次换抬腿时重心都会横跳，不稳。

### 4.5 Gait_Update() — 每帧调用

```c
void Gait_Update(void)
{
    // 1. 相位推进
    uint32_t dt = now - g_last_ms;
    uint32_t advance = GAIT_CYCLE_MS / 360;   // 每度耗时 ms
    if (advance > 0 && dt >= advance) {
        g_phase = (g_phase + (uint16_t)(dt / advance)) % 360;
        g_last_ms = now;
    }

    // 2. 逐腿计算 + 输出
    for (int leg = 0; leg < 4; leg++) {
        uint16_t local_phase = (g_phase + offset[leg]) % 360;

        // 调用轨迹函数 → thigh_delta, calf_delta

        // 叠加站立角
        uint16_t thigh = CLAMP(STAND_POSE[leg][JOINT_THIGH] + thigh_delta, ...);
        uint16_t calf  = CLAMP(STAND_POSE[leg][JOINT_CALF]  + calf_delta,  ...);

        // 写入舵机
        Leg_SetJoint(leg, JOINT_ABD,   ABD_ANGLE_STAND);
        Leg_SetJoint(leg, JOINT_THIGH, thigh);
        Leg_SetJoint(leg, JOINT_CALF,  calf);
    }
}
```

**为什么相位推进用 `dt / advance` 而不是固定增量？**

因为主循环帧率不固定——摄像头 DMA 忙时会拖慢循环。如果每次固定 +1°，帧率快慢会导致步态周期不对。用 `dt` 自适应：帧快就多加，帧慢就少加，保证实际周期总是 ≈ `GAIT_CYCLE_MS`（800ms）。

**为什么 `g_last_ms = now` 在 STAND 模式下也更新？**

防止切换步态时累积一大段 `dt` 导致相位跳变。STAND 下不推进相位，但时间基准要保持最新。

**为什么外展 `ABD_ANGLE_STAND` 每帧都重写？**

当前框架下外展不动，但"重写"不浪费——`__HAL_TIM_SET_COMPARE` 写同一个值只是改了寄存器，舵机不会抖动。保留这个调用是为了后续扩展：加侧移/转弯时只需把常值换成变量。

### 4.6 CLAMP 宏

```c
#define CLAMP(x, min, max)  ((x) < (min) ? (min) : ((x) > (max) ? (max) : (x)))
```

**为什么要限幅？** 轨迹函数算出的 `thigh_delta` 可能让最终角度超出舵机物理限位。比如站立角 150°，步幅 ±40，极端情况 190°——还在 30~240 范围内，OK。但如果步幅调到 60，190 就超了，CLAMP 兜底防止舵机撞限位烧毁。

## 五、参数调优指南 (leg_config.h)

### 5.1 站立姿态 STAND_POSE

```c
static const uint16_t STAND_POSE[4][3] = {
    { 135, 150, 120 },  // Leg 1: 外展135°, 大腿150°, 小腿120°
    ...
};
```

这六个数字需要实物标定。当前是预估值，实际装好腿后需要逐腿微调——因为舵机安装角度不可能一模一样。

**标定方法：**
1. 蓝牙发 `A5 01 01 5A` 切 STAND 步态
2. 观察每条腿是否竖直着地、身体是否水平
3. 微调 `STAND_POSE[leg][JOINT_THIGH]` ±5，直到四腿均匀受力

### 5.2 关节限幅

```c
#define THIGH_ANGLE_MIN  30
#define THIGH_ANGLE_MAX 240
```

**为什么大腿范围比外展大（30~240 vs 60~210）？**

大腿是前后摆动的主力关节，需要大范围。外展只负责侧向微调和站立，不需要太大范围。但注意 30 和 240 只是"安全不撞"的软限，实际舵机能到 0 和 270——只是到了极限位会撞机械结构。

### 5.3 步态参数

```c
#define GAIT_STEP_HEIGHT  30   // 抬腿高度(角度)
#define GAIT_STEP_LENGTH  40   // 步幅(角度)
#define GAIT_CYCLE_MS    800   // 周期(ms)
```

| 参数 | 调大后果 | 调小后果 |
|------|---------|---------|
| STEP_HEIGHT | 抬得高 → 过障碍强，但力矩需求大 | 抬得低 → 省力，但容易拖地 |
| STEP_LENGTH | 步子大 → 走得快，但关节可能到极限 | 步子小 → 慢但稳 |
| CYCLE_MS | 周期长 → 动作慢但平滑，舵机跟得上 | 周期短 → 快但舵机可能反应不及 |

**推荐调试顺序：** 先 CYCLE_MS=1200（慢速），STEP_HEIGHT=20（低抬），STEP_LENGTH=20（小步），确认四条腿动作方向对。再逐步加速加大。

## 六、如何修改

### 场景 1：加新步态（比如 GALLOP 奔跑）

只需改三处：

**(1)** `gait.h` 枚举加一项：
```c
typedef enum {
    GAIT_STAND = 0,
    GAIT_TROT,
    GAIT_WALK,
    GAIT_CRAWL,
    GAIT_GALLOP,   // ← 新增
    GAIT_NUM
} GaitType;
```

**(2)** `gait.c` offset 表加一行：
```c
static const uint16_t gait_offsets[GAIT_NUM][4] = {
    ...
    /* GALLOP */ {   0,  60, 180, 240 },
};
```

**(3)** `main.c` `bt_on_command` 加一个 case：
```c
case 0x05: Gait_SetType(GAIT_GALLOP); break;
```

三处改完，新步态就工作了——连轨迹函数都不用动。

### 场景 2：把三角波小腿轨迹改成真正弦

**(1)** 在 `gait.c` 头部加正弦查找表：
```c
// 0~90° 正弦值 × 100（90 个点，够用）
static const int16_t sin_table[91] = { 0, 2, 3, 5, 7, ... , 100 };
```

**(2)** 替换 `swing_traj` 的小腿计算：
```c
// 旧: 三角波
*calf_delta = (int16_t)(GAIT_STEP_HEIGHT * phase) / 90;

// 新: 查表正弦
uint16_t idx = (phase <= 90) ? phase : (180 - phase);
*calf_delta = (int16_t)(GAIT_STEP_HEIGHT * sin_table[idx]) / 100;
```

只改一个函数，其他全部不动。

### 场景 3：加侧移/转弯

目前外展 `ABD_ANGLE_STAND` 是写死的常量。要做出左右移动，需要：

**(1)** `gait.c` 加一个全局变量 `g_abd_target[4]`

**(2)** `Gait_Update()` 里把：
```c
Leg_SetJoint(leg, JOINT_ABD, ABD_ANGLE_STAND);
```
改成：
```c
Leg_SetJoint(leg, JOINT_ABD, g_abd_target[leg]);
```

**(3)** 蓝牙命令切换时改变 `g_abd_target`，比如向左移：
```c
g_abd_target[0] = ABD_ANGLE_STAND + 20;  // 左前腿外展
g_abd_target[1] = ABD_ANGLE_STAND - 20;  // 右前腿内收
...
```

### 场景 4：换舵机型号

如果换成 180° 舵机，只改 `new_servo.c` 的映射公式和 `leg_config.h` 的范围宏——往上两层完全不变。

## 七、关键设计原则总结

| 原则 | 体现 |
|------|------|
| **分层隔离** | gait → leg_control → new_servo, 每层只调下一层 |
| **整数运算** | 全程无 float, 避免 nano.specs 浮点问题 |
| **数据驱动** | 步态差异 = offset 数组的一行数字, 不加代码 |
| **自适应时间** | dt 驱动相位而非固定增量, 帧率无关 |
| **限幅兜底** | CLAMP 防止轨迹计算错误导致舵机超限 |
